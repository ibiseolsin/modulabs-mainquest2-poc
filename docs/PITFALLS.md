# 만들면서 걸린 것들

숫자가 나온다는 것과 그 숫자가 의도한 것을 재고 있다는 것은 다릅니다.
이 PoC에서 실제로 겪은 것을 순서대로 남깁니다.

---

## 1. 정답이 얼굴이 아니었다

**증상.** 합성 데이터셋 12장 / 얼굴 60개를 만들고 `ground_truth.json`까지 정상으로 떨어졌습니다. 장당 5개, 총 60개. 숫자만 보면 문제가 없습니다.

**그런데 이미지를 열어 보니** 붙여넣은 다섯 개 중 넷이 얼굴이 아니라 색색의 줄무늬 노이즈 덩어리였습니다.

![정답이 얼굴이 아니었던 상태](assets/pitfall_bad_faces.jpg)

**원인.** 얼굴을 **256px로 직접 생성**했습니다. Stable Diffusion 1.5는 512×512로 학습된 모델이라 256으로 생성하면 구조가 무너집니다. 512로 만든 뒤 붙일 크기로 줄이면 정상입니다.

**이걸 놓쳤다면.** 탐지기 셋을 돌려 "재현율 12%" 같은 숫자를 받고, 모델이 나쁘다고 결론 냈을 것입니다. **실제로는 정답 쪽이 틀렸습니다.** 채점표가 틀리면 그 표로는 아무것도 판단할 수 없습니다.

**교훈.** 자료를 만드는 단계에도 검산이 필요합니다. 그래서 `build_dataset.py`가 얼굴 풀을 `data/face_pool/`과 `face_pool_contact.png`로 따로 저장하도록 고쳤습니다. **붙이기 전에 눈으로 보게 만드는 것**이 가장 빠른 검산입니다.

## 2. 정답 상자가 얼굴보다 컸다 — 모델이 아니라 채점표가 틀렸다

**증상.** 탐지 후보 셋을 돌렸더니 재현율이 Haar 41.7%, YuNet 50.0%, YOLO 31.7%로 나왔습니다. 성공 기준 95%에 한참 못 미칩니다. 숫자만 보면 **"세 후보 다 못 쓴다"** 는 결론입니다.

**그런데 시각화를 열어 보니** 파란 예측 상자가 얼굴마다 정확히 붙어 있었습니다. **YuNet은 얼굴을 다 찾았는데 놓쳤다고 세어지고 있었습니다.**

![정답 상자가 얼굴보다 컸던 상태](assets/pitfall_gt_toobig.jpg)

**원인.** 정답 상자를 **붙여넣은 정사각형 전체**로 잡았습니다. 그 정사각형에는 얼굴뿐 아니라 머리카락과 인물 사진의 배경이 함께 들어 있습니다. 탐지기는 얼굴만 잡으므로, 정답 넓이 대비 덮인 비율이 0.4 근처에 머물러 `cover_thr=0.5`를 못 넘었습니다.

**여기서 하면 안 되는 것.** `cover_thr`을 0.35로 낮추면 숫자가 좋아집니다. 하지만 그건 **결과를 본 뒤에 채점 기준을 결과 쪽으로 기울이는 것**이고, 그렇게 만든 채점표로는 아무것도 판단할 수 없습니다.

**해결.** 정답을 고쳤습니다. 얼굴 풀 8장을 격자와 함께 띄워 놓고 **얼굴이 실제로 차지하는 영역을 눈으로 읽어 손으로 적었습니다** (`build_dataset.py`의 `FACE_BOXES`). 합성할 때 이 비율을 붙이는 크기에 곱해 정답 상자를 만듭니다.

정답은 모델이 정하는 것이 아니라 사람이 정합니다. 그리고 **모델을 돌리기 전에** 정해야 합니다.

**교훈.** 기준에 못 미치는 결과가 나왔을 때 첫 질문은 "모델이 나쁜가"가 아니라 **"채점표가 맞는가"** 입니다. 이 확인을 건너뛰면 멀쩡한 후보를 탈락시킵니다. 그리고 이걸 잡아낸 것은 집계 숫자가 아니라 **상자를 그려 놓은 이미지**였습니다. `build_dataset.py`가 이제 `data/gt_vis/`에 정답 오버레이를 함께 저장하는 이유입니다.

## 3. torchvision이 torch와 어긋나 있었다

**증상.** `RuntimeError: operator torchvision::nms does not exist`, 그리고 그 여파로 `Could not import module 'CLIPImageProcessor'`.

**원인.** CUDA 빌드를 `pip install --upgrade torch --index-url .../cu128`로 설치했는데, cu128 인덱스의 최신이 `2.11.0+cu128`이고 이미 깔려 있던 CPU 빌드가 `2.13.0`이었습니다. pip은 **더 높은 버전이 이미 있다고 보고 업그레이드를 건너뛰었습니다.** 그 결과 torch(CPU 2.13)와 torchvision(cu128 0.26)이 짝이 안 맞는 상태로 남았습니다.

**해결.** 버전을 명시해 짝으로 강제 재설치했습니다.

```bash
pip install --force-reinstall --no-deps --index-url https://download.pytorch.org/whl/cu128 "torch==2.11.0+cu128" "torchvision==0.26.0+cu128"
```

**교훈.** `--upgrade`는 "이 인덱스의 것으로 바꿔라"가 아니라 "더 높은 버전이면 올려라"입니다. 별도 인덱스의 빌드로 바꿀 때는 버전을 박아야 합니다.

## 4. IoU로 채점하면 후보 하나가 부당하게 진다

**증상은 아직 없지만 설계 단계에서 걸러낸 것.** 탐지 채점의 표준은 IoU(교집합/합집합)입니다. 그런데 후보 중 `yolo_person`은 **얼굴이 아니라 사람 전체**를 잡습니다. 정답이 얼굴 상자이므로 IoU는 0.1 근처로 깔립니다.

IoU로 줄을 세우면 `yolo_person`이 꼴찌로 나옵니다. **하지만 이 업무의 판정은 "상자가 정확히 맞느냐"가 아니라 "그 얼굴이 가려지느냐"입니다.** 사람 전체를 가려도 얼굴은 가려집니다.

그래서 채점 기준을 **정답 얼굴 넓이 중 예측에 덮인 비율(coverage)** 로 바꿨습니다 (`detect_faces.py`의 `covered()`).

```
IoU        = 교집합 / 합집합      ← 상자가 얼마나 정확한가
coverage   = 교집합 / 정답넓이    ← 그 얼굴이 가려지는가   ← 이 업무는 이것
```

대신 사람 전체를 가리면 **가리는 넓이가 커져 사진이 못 쓰게 되는** 손해가 생깁니다. 그건 coverage로는 안 잡히므로 `장당 오탐`과 SAM 단계의 `마스크 화소 비율`로 따로 봅니다.

**교훈.** 채점 기준을 업무의 판정 항목에서 가져와야 합니다. 표준 지표를 그대로 쓰면 업무와 다른 것을 재게 됩니다.

## 5. 성공 기준을 정확도로 잡으면 도입할 값이 없다

이 업무는 **미탐과 오탐의 비용이 비대칭**입니다.

- 놓친 얼굴 → 그대로 공개 → 되돌릴 수 없음
- 잘못 잡은 영역 → 담당자가 클릭 한 번으로 제외

정확도(precision과 recall의 균형)로 기준을 잡으면 오탐을 줄이는 방향으로 임계값이 조여지고, 그러면 작은 얼굴을 놓칩니다. 그래서 성공 기준을 **재현율 우선**으로 쓰고, 오탐은 "장당 2개 이하"라는 별도의 느슨한 상한만 걸었습니다.

자세한 것은 [PROBLEM.md](PROBLEM.md)의 성공 기준 절에 있습니다.

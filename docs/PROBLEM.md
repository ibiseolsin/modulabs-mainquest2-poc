# 문제 정의서

> **강의 자료용 현장 사진의 개인정보 마스킹 후보 자동 탐지**
> 2026-08-14 · 김지훈

## ⚠️ 시작하기 전에 — 이 업무 상황은 가상입니다

저는 지금 맡고 있는 실무가 없는 **모두의연구소 AI 에이전트 1기 수강생**입니다. 그래서 실제 담당 업무 대신 **캠프 운영팀의 콘텐츠 제작 업무를 가상으로 설정**해서 문제 정의부터 검증까지 진행했습니다.

아래에 나오는 **업무 절차, 발생량, 처리 시간, 누락률은 전부 제가 잡은 가정값**입니다. 운영팀에 물어보거나 실제로 재 본 값이 아니에요.

**실제로 검증한 건 기술적 타당성 하나**입니다. "얼굴 탐지 모델로 마스킹 후보를 찾아낼 수 있는가"는 코드랑 숫자로 확인했지만, "이 업무에 도입할 값이 있는가"는 현행 수준을 잴 수가 없어서 **판단하지 않았습니다.**

무엇이 가정이고 무엇이 측정인지는 [0-3절](#0-3-무엇이-가정이고-무엇이-실제인가)에 갈라놨습니다.

## 0. 도메인을 이렇게 고른 맥락

### 0-1. 왜 가상 상황으로 갔나

과제는 "일하거나 **자세히 아는** 도메인"을 요구합니다. 네 갈래를 놓고 고민했어요.

| 후보 | 왜 봤나 | 판정 |
| --- | --- | --- |
| 현재 담당 실무 | 가장 정확하게 쓸 수 있음 | ❌ **해당 없음.** 지금 맡은 실무가 없음 |
| 개인 자료 정리 (사진첩, 가계부) | 자료가 다 내 손에 있어 실측이 가능 | △ 되긴 하는데 발생량이 작아 개선 효과가 눈에 안 띔 |
| 일반 사무 업무 (문서 정리, 메일 분류) | 누구나 겪는 병목이라 공감이 쉬움 | ❌ 내가 아는 현장이 아님. 결국 상상으로 써야 함 |
| **캠프 운영 (가상 설정)** | 도메인의 **구조**는 안에서 보고 있음. 업무 유형이 다양해 후보 비교가 됨 | ✅ **선정** — 가정임을 밝히는 조건으로 |

첫 줄이 비어 있다는 게 출발점이었습니다. 그래서 **실무가 있는 척하는 대신, 가상임을 밝히고 그 안에서 최대한 정확하게 쓰는 쪽**을 택했습니다.

### 0-2. 왜 하필 이 도메인을 무대로 골랐나

아무 데나 지어내면 문제 정의서가 통째로 상상이 되니까, 그나마 **구조를 아는** 곳으로 잡았습니다.

**하나, 도메인의 뼈대는 안에서 보고 있습니다.** 수강생으로서 캠프가 어떻게 굴러가는지 — 강의·과제·문의·행사가 어떤 흐름으로 도는지 — 는 매주 겪습니다. 개별 업무의 내부 절차는 모르지만, **어떤 업무들이 존재하는지**는 상상이 아니에요.

**둘, 업무 유형이 네 가지에 고르게 걸쳐 있습니다.** 강의가 정리한 네 유형이 이 도메인 안에 다 있습니다. 문의 분류는 *분류와 배분*, 과제 채점은 *검사와 판독*, 자료 검색은 *검색*, 강의 녹화 자막은 *입력과 전사*. 후보를 셋 이상 뽑으라는 요구를 억지로 짜내지 않고 채울 수 있었습니다.

**셋, "되돌릴 수 없는 업무"가 실제로 있습니다.** 강의는 되돌릴 수 없는 업무를 PoC에서 빼라고 하면서, 동시에 그런 업무에선 AI를 "후보만 좁혀 사람에게 넘기는 앞단"에 넣으라고 합니다. 교육 도메인은 성적·수료·개인정보처럼 **한 번 나가면 못 주워 담는 판정**이 있어서 이 구분을 연습하기 좋았습니다. 실제로 이 PoC의 설계가 여기서 갈렸고요.

### 0-3. 무엇이 가정이고 무엇이 실제인가

이 문서에서 제일 중요한 표입니다.

| | 내용 | |
| --- | --- | --- |
| 🔸 **가정** | 운영팀이 행사 사진의 얼굴을 수작업으로 가린다 | 실제 절차를 확인한 적 없음. 이미 도구를 쓰고 있을 수도 |
| 🔸 **가정** | 행사당 200~500장, 장당 1~3분 | 일반적인 행사 촬영량에서 잡은 값 |
| 🔸 **가정** | 현행 누락률 5% 안팎 | **성공 기준 95%의 근거인데, 그 근거가 가정** |
| 🔸 **가정** | 과거 마스킹 이력이 남아 있다 | 확인 불가 |
| 🔹 **실제** | 후보 셋의 탐지 성능 (75.0 / 96.7 / 41.7%) | 코드로 측정. seed 고정이라 재현됨 |
| 🔹 **실제** | SAM으로 가리는 넓이 29.3% 감소 | 화소 수로 측정 |
| 🔹 **실제** | 외부 API가 개인정보 조건에서 탈락한다는 판단 | 자료 성격상 성립하는 논리 |
| 🔹 **실제** | 합성 데이터 60개 얼굴과 그 정답 | 저장소에 포함, 눈으로 검증 |

정리하면 이렇습니다.

- **기술 검증은 진짜입니다.** 모델이 얼굴을 찾는지, 후보 중 뭐가 나은지는 실제로 재서 나온 숫자예요.
- **업무 개선 효과는 아무것도 증명 못 했습니다.** "전"을 잰 적이 없으니 "얼마나 좋아졌다"를 말할 수가 없습니다.

이 구분을 앞에 박아두는 이유는, 가정값을 실측값처럼 써두면 나중에 읽는 사람이 "이미 확인된 것"으로 받아들이고 그 위에 결정을 쌓기 때문입니다. **어디까지 재 본 건지가 문서에 남아 있어야 해요.**

### 0-4. 실무였다면 이 순서였어야 합니다

강의는 "기준을 적기 전에 현행 수준을 먼저 재라"고 합니다. 가상 상황이라 이걸 지킬 수가 없었고, 그래서 성공 기준의 근거가 비어 있습니다.

실무였다면 **코드를 짜기 전에** 이랬어야죠.

1. 담당자한테 사진 50장을 처리하게 하고 **걸린 시간이랑 누락 수를 센다**
2. 그 숫자로 성공 기준을 쓴다 — 사람이 2% 놓치면 기준은 98%지, 95%가 아니다
3. **그다음에** 후보를 고르고 만든다

이 PoC는 1·2번을 건너뛰고 3번부터 했습니다. **가장 큰 구조적 한계이고, 가상 상황이라는 전제에서 나온 결과입니다.**

## 1. 도메인 (가정)

**모두의연구소 캠프 운영 — 학습 콘텐츠 제작·운영**

캠프를 굴리다 보면 사진이 계속 쌓입니다. 오프라인 밋업, 해커톤, 수료식, 팀 프로젝트 발표. 이 사진들은 다음 기수 모집 페이지나 블로그 후기, 커리큘럼 소개 자료, SNS 홍보물로 나갑니다.

문제는 사진에 수강생 얼굴이 그대로 찍혀 있다는 거죠. 밖에 내보내려면 **동의 안 받은 사람 얼굴을 가려야 합니다.** 동의한 사람과 안 한 사람이 한 프레임에 섞여 있고, 뒤로 지나가던 사람까지 찍히고요.

## 2. 지금 어떻게 하고 있나 (가정)

콘텐츠 담당자가 사진을 하나씩 이미지 편집기로 엽니다. 눈으로 훑어 얼굴을 찾고, 가려야 할 것에 블러나 모자이크를 얹고, 저장. 이걸 반복합니다.

번거로운 지점이 셋입니다.

**총량.** 행사 한 번에 200~500장이 나옵니다. 장당 1~3분이면 하루가 통째로 들어가요. 판단 자체는 어렵지 않습니다. "얼굴이면 가린다"가 전부니까요. 병목은 판단의 난이도가 아니라 **판단의 개수**입니다.

**누락.** 사람이 지치면 뒷줄의 작은 얼굴, 창문에 비친 얼굴, 노트북 화면 속 화상회의 참가자를 놓칩니다. **한 장만 놓쳐도 유출이고**, 공개된 뒤엔 되돌리기 어렵습니다.

**일관성.** 담당자가 바뀌면 "이 정도 크기는 안 가려도 되나"의 기준이 달라집니다.

급할 땐 사진 전체에 약한 블러를 얹거나, 얼굴 많이 나온 사진을 그냥 버립니다. 둘 다 자료의 가치를 깎죠.

## 3. 개선 가설

> **얼굴 탐지 모델로 "가려야 할 후보"를 먼저 찾아 주면, 담당자는 찾는 일에서 확인하는 일로 옮겨간다.**

파이프라인의 **어디에** 넣는지가 중요합니다.

```
[지금]  사진 → 사람이 찾는다 → 사람이 가린다 → 저장
[개선]  사진 → 모델이 후보를 찾는다 → 사람이 확인·가감한다 → 자동 마스킹 → 저장
                  ~~~~~~~~~~~~~~~~~~     ~~~~~~~~~~~~~~~~~~~
                  여기만 자동화           여기는 사람이 유지
```

**최종 판정은 모델한테 안 넘깁니다.** 공개된 사진은 되돌릴 수 없으니까요. 모델이 하는 일은 **후보를 좁혀 사람에게 넘기는 앞단**까지고, 확인 버튼은 사람이 누릅니다.

이 설계 때문에 실수의 무게가 한쪽으로 쏠립니다.

| | 결과 | 비용 |
| --- | --- | --- |
| **놓침 (미탐)** | 가려야 할 얼굴이 그대로 공개 | 💀 **치명적. 되돌릴 수 없음** |
| **잘못 잡음 (오탐)** | 얼굴 아닌 곳이 후보로 표시 | 🤷 클릭 한 번으로 제외 |

그래서 도입 근거를 **정확도가 아니라 재현율(recall)** 로 잡았습니다. 오탐은 넉넉히 허용하고 미탐을 0에 가깝게 만드는 게 목표예요. 정확도로 기준을 잡으면 이 업무에선 "도입할 값이 없다"는 엉뚱한 결론이 나옵니다.

## 4. 누가 도움받나

| 사용자 | 지금 | 개선 후 |
| --- | --- | --- |
| **콘텐츠 제작 담당자** (주 사용자) | 200~500장을 눈으로 훑으며 얼굴을 찾음. 하루 소요 | 후보가 표시된 상태에서 확인만. 찾는 일 → 확인하는 일 |
| **캠프 운영 매니저** | 공개 전 검수 때 누락을 다시 확인해야 함 | 탐지 로그(장별 후보 수·신뢰도)가 남아 검수 근거가 됨 |
| **수강생** (최종 수혜자) | 동의 안 한 사진이 공개될 위험 | 누락 위험이 줄어듦 |

## 5. 성공 기준

만들기 **전에** 적었습니다. 정량으로요.

> **① 재현율** — 정답 얼굴 60개 중 57개 이상 잡는다 (미탐 ≤ 3, 재현율 ≥ 95%)
> **② 처리 시간** — 장당 수작업보다 짧다
> **③ 오탐** — 장당 평균 2개 이하. 지우는 부담이 찾는 부담보다 작아야 한다

**숫자를 이렇게 잡은 이유.**

**①의 95%** 는 현행 수작업의 누락률에서 왔습니다. 사람이 200장을 연속으로 처리하면 후반부에 작은 얼굴을 놓치기 시작한다고 보고 그 비율을 5% 안팎으로 잡았어요. **사람보다 못하면 도입할 이유가 없으니까** 최소한 같은 수준인 95%를 하한으로 뒀습니다.

> ⚠️ **근데 이 5%가 가정값입니다.** 가상 상황이라 현행 수준을 잴 대상 자체가 없었어요([0-3절](#0-3-무엇이-가정이고-무엇이-실제인가)). 즉 **성공 기준의 근거가 비어 있고, 따라서 "기준을 넘었다"가 "도입할 값이 있다"를 뜻하지 않습니다.** 이 PoC의 제일 약한 고리예요.

**③의 2개** 는 "오탐 지우는 시간 < 직접 찾는 시간"이 성립하는 대략의 경계입니다. 장당 오탐이 5개를 넘어가면 담당자가 후보를 못 믿고 결국 처음부터 다시 훑게 되거든요.

**기준에 안 넣은 것.** 마스킹이 시각적으로 자연스러운지는 판정 항목에서 뺐습니다. 항목을 늘리면 각각 기준을 따로 세워야 하고, 그중엔 기준 세울 자료가 없는 것도 생겨요. PoC는 **탐지 하나가 되는지** 확인하는 단계입니다.

## 제약 조건 — 점수랑 안 섞고 먼저 거르는 것

이 둘은 성능이 얼마든 후보를 탈락시키는 조건입니다. 점수 계산에 감점으로 넣으면, 다른 항목이 높을 때 쓸 수 없는 후보가 1위로 올라오거든요.

**실행 위치.** 입력이 **수강생 얼굴이 담긴 원본 사진**입니다. 가리기 전 상태를 밖으로 보내는 건 이 업무의 목적과 정면으로 충돌하죠. → **외부 클라우드 Vision API는 성능 재기 전에 제외.**

**라이선스.** 후보 중에 배포 조건이 AGPL인 게 있습니다(Ultralytics YOLO). 사내 사용은 괜찮은데, 닫힌 제품에 넣어 배포하면 소스 공개 의무가 걸립니다. 만든 쪽이 그걸 면제해주는 상용 라이선스를 따로 팔고요. **지금 용도는 통과. 외부 배포 계획이 생기면 여기서 결정이 납니다.**

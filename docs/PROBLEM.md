# 문제 정의서

> 강의 자료용 현장 사진의 개인정보 마스킹 후보 자동 탐지
> 작성일: 2026-08-14 · 작성: 김지훈

---

## 1. 도메인 설명

**모두의연구소 캠프 운영 — 학습 콘텐츠 제작·운영**

캠프를 운영하면 사진이 계속 쌓입니다. 오프라인 밋업, 해커톤, 수료식, 팀 프로젝트 발표. 이 사진들은 다음 기수 모집 페이지, 블로그 후기, 커리큘럼 소개 자료, SNS 홍보물에 쓰입니다.

사진에는 수강생 얼굴이 그대로 찍혀 있습니다. 외부에 공개하려면 **동의하지 않은 인물의 얼굴을 가려야 합니다.** 촬영 동의를 받은 인원과 안 받은 인원이 한 프레임에 섞여 있고, 뒷줄에 지나가던 사람까지 찍힙니다.

## 2. 현재의 문제

**지금은 이렇게 합니다.** 콘텐츠 담당자가 사진을 하나씩 이미지 편집기로 엽니다. 눈으로 훑어 얼굴을 찾고, 가려야 할 얼굴에 블러나 모자이크를 얹고, 저장합니다.

**번거로운 지점은 셋입니다.**

- **총량.** 행사 한 번에 200~500장이 나옵니다. 장당 1~3분이면 하루가 통째로 들어갑니다. 판단 자체는 어렵지 않습니다. "얼굴이면 가린다"가 전부입니다. 병목은 판단의 난이도가 아니라 **판단의 총량**입니다.
- **누락.** 사람이 지치면 뒷줄의 작은 얼굴, 창문에 비친 얼굴, 노트북 화면 속 화상회의 참가자를 놓칩니다. **한 장만 놓쳐도 유출입니다.** 그리고 공개된 뒤에는 되돌리기 어렵습니다.
- **일관성.** 담당자가 바뀌면 "이 정도 크기는 안 가려도 되나"의 기준이 달라집니다.

**지금 급할 때 쓰는 대안**은 사진 전체에 약한 블러를 얹거나, 얼굴이 많이 나온 사진을 아예 버리는 것입니다. 둘 다 자료의 가치를 깎습니다.

## 3. 개선 가설

> **얼굴 탐지 모델을 넣어 "가려야 할 후보 영역"을 먼저 찾아 주면, 담당자는 찾는 일에서 확인하는 일로 옮겨간다.**

파이프라인의 어느 단계에 넣는지가 중요합니다.

```
[현재]  사진 → 사람이 찾는다 → 사람이 가린다 → 저장
[개선]  사진 → 모델이 후보를 찾는다 → 사람이 확인·가감한다 → 자동 마스킹 → 저장
                     ~~~~~~~~~~~~~~~~~~   ~~~~~~~~~~~~~~~~~
                     여기를 자동화        여기는 사람이 유지
```

**최종 판정을 모델에게 주지 않습니다.** 공개된 사진은 되돌릴 수 없으므로, 모델이 하는 일은 **후보를 좁혀 사람에게 넘기는 앞단**까지입니다. 최종 확인 버튼은 사람이 누릅니다.

이 설계 때문에 **비용이 비대칭입니다.**

| | 결과 | 비용 |
| --- | --- | --- |
| **놓침 (미탐)** | 가려야 할 얼굴이 그대로 공개 | **치명적. 되돌릴 수 없음** |
| **잘못 잡음 (오탐)** | 얼굴 아닌 곳이 후보로 표시 | 담당자가 클릭 한 번으로 제외 |

그래서 이 문제의 도입 근거는 **정확도가 아니라 재현율(recall)** 입니다. 오탐은 넉넉히 허용하고 미탐을 0에 가깝게 만드는 것이 목표입니다. 정확도로 기준을 잡으면 이 업무에서는 도입할 값이 없다는 잘못된 결론이 납니다.

## 4. 대상 사용자

| 사용자 | 지금 겪는 것 | 개선 후 |
| --- | --- | --- |
| **콘텐츠 제작 담당자** (주 사용자) | 200~500장을 눈으로 훑으며 얼굴을 찾음. 하루가 소요 | 후보가 표시된 상태에서 확인만. 찾는 일 → 확인하는 일 |
| **캠프 운영 매니저** | 공개 전 검수 시 누락을 다시 확인해야 함 | 탐지 로그(장별 후보 수·신뢰도)가 남아 검수 근거가 됨 |
| **수강생** (최종 수혜자) | 동의하지 않은 사진이 공개될 위험 | 누락 위험이 줄어듦 |

## 5. 성공 기준

만들기 전에 적었습니다. 정량으로 씁니다.

> ### **① 재현율: 정답 얼굴 60개 중 57개 이상을 후보로 잡는다 (미탐 ≤ 3, 재현율 ≥ 95%)**
> ### **② 처리 시간: 장당 수작업 시간보다 짧다**
> ### **③ 오탐은 장당 평균 2개 이하 — 담당자가 지우는 부담이 확인하는 부담보다 작아야 한다**

**숫자의 근거.**

- **①의 95%**는 현행 수작업의 누락률에서 왔습니다. 담당자가 200장을 연속으로 처리할 때 후반부에 작은 얼굴을 놓치는 비율이 경험적으로 5% 안팎입니다. **사람보다 못하면 도입할 값이 없으므로** 최소한 같은 수준인 95%를 하한으로 잡았습니다.
  - ⚠️ 이 5%는 **실측값이 아니라 담당자 진술 기반 추정치**입니다. 실제 도입 판단 전에는 담당자에게 사진 50장을 처리하게 하고 누락 수를 세어 다시 써야 합니다. 이 PoC의 가장 약한 고리입니다.
- **③의 2개**는 "오탐을 지우는 시간 < 직접 찾는 시간"이 성립하는 대략의 경계입니다. 장당 오탐이 5개를 넘으면 담당자가 후보를 신뢰하지 않고 결국 처음부터 다시 훑게 됩니다.

**성공 기준에 넣지 않은 것.** 마스킹의 시각적 품질(경계가 자연스러운가)은 이 PoC의 판정 항목이 아닙니다. 판정 항목을 늘리면 항목마다 기준을 따로 세워야 하고, 기준을 세울 자료가 없는 항목이 생깁니다. PoC는 **탐지 하나가 되는지** 확인하는 단계입니다.

## 제약 조건 (점수와 섞지 않고 먼저 거르는 항목)

이 둘은 성능이 얼마든 후보를 제외시키는 조건입니다. 점수 계산에 감점으로 넣으면, 다른 항목이 높을 때 쓸 수 없는 후보가 1위로 올라옵니다.

**실행 위치.** 입력이 **수강생 얼굴이 담긴 원본 사진**입니다. 마스킹하기 전 상태를 외부로 보내는 것은 이 업무의 목적과 정면으로 충돌합니다. → **외부 클라우드 Vision API 후보는 성능 측정 전에 제외.**

**라이선스.** 후보 중 배포 조건이 AGPL인 것이 있습니다(Ultralytics YOLO). 사내 업무 사용은 문제가 없지만, 닫힌 제품에 넣어 배포하면 소스 공개 의무가 걸립니다. 만든 쪽이 그 의무를 없앤 상용 라이선스를 별도 판매합니다. **현재 용도(사내 콘텐츠 제작)는 통과. 외부 배포 계획이 생기면 여기서 다시 결정해야 합니다.**

## 이 지점을 고른 이유 (후보 3곳 중)

| 후보 지점 | 업무 유형 | 판정 기준 | 판정 기록 | 되돌리기 | 발생량 | 판정 |
| --- | --- | --- | --- | --- | --- | --- |
| **A. 사진 개인정보 마스킹** | 검사와 판독 | ✅ "얼굴이면 가린다" 명확 | ✅ 과거 마스킹본 존재 | ⚠️ 공개 후엔 어려움 → **사람 확인 단계 유지로 해소** | ✅ 행사당 200~500장 | **선정** |
| B. 과제 제출물 채점 보조 | 검사와 판독 | ❌ 튜터 간 해석이 갈림 | ✅ | ❌ 성적에 직접 영향 | ⚠️ 기수당 몰림 | 제외 |
| C. 수강생 문의 1차 분류 | 분류와 배분 | ✅ | ✅ | ✅ | ✅ | 탐색 후 제외 |

- **B**를 뺀 이유: 판정 기준이 사람마다 다릅니다. 필요한 것은 모델이 아니라 **루브릭을 다시 문서로 만드는 작업**입니다.
- **C**를 뺀 이유: 네 기준을 다 만족해서 먼저 PoC를 만들어 봤습니다. 그런데 **키워드 규칙 기준선이 18/20으로 이겼습니다.** "이 업무에는 지금 방식이 낫다"가 결론이고, 그것도 결과입니다. 기록은 [`explore_text_triage/REPORT.md`](../explore_text_triage/REPORT.md)에 남겼습니다.
- **A**의 "되돌릴 수 없음"은 설계로 해소했습니다. 모델을 최종 판정이 아니라 후보 제시 단계에만 넣습니다.
